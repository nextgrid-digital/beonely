# Beonely Security Audit and Remediation Register

Audit date: 11 July 2026
Scope: application source, Vercel functions, Supabase migrations and Storage policies, payment and email integrations, dependencies, tests, build output, and administration UX.
Status meaning: **Fixed in repository** means the source and forward migrations contain the remediation. It does not mean those migrations or environment changes have already been deployed.

## Executive result

The review found critical authorization, payment, and email-delivery risks in the original implementation, plus high-severity privacy, consent, webhook, and race-condition issues. The repository now places privileged administration behind an allowlisted server API, exposes narrow public projections, uses atomic/idempotent payment and email workflows, protects candidate assets, and has automated quality gates.

Current source-level result:

- 3 critical findings fixed in repository.
- 10 high findings fixed in repository.
- 12 medium findings fixed in repository.
- 8 low/quality findings fixed in repository.
- Production dependency audit reports no known vulnerabilities.
- Remaining items are deployment and operational validation steps, not known unfixed source vulnerabilities.

## Severity definitions

- **Critical:** direct privilege escalation, arbitrary external action, or loss of payment integrity with broad impact.
- **High:** exposure or modification of sensitive data, consent bypass, signed-event bypass, or reliable cross-account abuse.
- **Medium:** abuse resistance, replay/race, operational integrity, or defense-in-depth weakness with meaningful impact.
- **Low:** limited-impact security hardening, reliability, accessibility, or maintainability weakness.

| H-01 | Anonymous job reads could expose base-table recruiter contact fields because RLS filters rows, not columns.           | Public disclosure of recruiter names/emails and operational fields.                                                | Anonymous clients now read the narrow `public_jobs` view; contact columns are redacted and disabled recruiters/expired listings are excluded. | H-05 | Certificates and application resumes had public or over-broad Storage access.                                         | Disclosure of personal resumes, qualifications, and private candidate material.                                    | Certificates/resumes use private owner-scoped paths and strict upload policies. | H-06 | Public portfolio, OG/share, avatar, and logo inputs accepted insufficiently constrained URLs/slugs.                   | SSRF-like server fetches, tracking pixels, malicious external schemes, oversized queries, or stored unsafe links.  | Server endpoints constrain slugs and never fetch arbitrary URLs. Logo rendering permits app-owned Storage or exact trusted LinkedIn CDN hosts. | H-07 | Transactional sends used check-then-send/check-then-insert patterns.                                                  | Duplicate receipts/reminders under concurrency or lost email after provider success and database failure.          | Delivery rows are atomically claimed with stale-retry support and fencing tokens; provider idempotency keys and explicit finalization make retries safe.                                                                                               | Fixed in repository |

| H-09 | Resend delivery failures and complaints were not consistently reflected in recipient suppression.                     | Continued sending to permanent bounces/complaints, reputation damage, and consent-policy violations.               | Signed webhook events update delivery state; complaints, suppression events, and permanent bounces suppress future sends.                                                                                                                              | Fixed in repository |

| M-07 | Payment email replay was skipped after a successful fulfillment record even when the earlier email failed. | Missing receipts and inconsistent customer communication.                             | Replays re-enter the deduplicated transactional dispatcher, which retries failed/stale claims but suppresses completed sends.                            | Fixed in repository |
| M-08 | Payment reporting did not represent refund/dispute/manual-review lifecycle clearly.                        | Misstated revenue and hidden operational exceptions.                                  | Payment lifecycle fields and admin revenue projections include capture, refund, dispute, failure, paid timestamp, manual-review reason, and net revenue. | Fixed in repository |
| M-09 | Job rejection could race an active checkout.                                                               | Customer pays after moderation made the listing ineligible.                           | API and database controls reject moderation when a non-expired checkout is outstanding; optimistic concurrency detects concurrent job changes.           | Fixed in repository |
| M-10 | Hiring-request notification recipients were hard-coded.                                                    | PII sent to the wrong mailbox across environments.                                    | Recipients now come from validated server-only `HIRING_REQUEST_NOTIFICATION_EMAILS`; failures are surfaced.                                              | Fixed in repository |
| M-11 | Scraped-job synchronization could expire valid listings after an unhealthy/partial scrape.                 | Availability loss and incorrect public listings.                                      | Missing-from-payload expiry is opt-in and guarded by scrape health/completeness; age and URL liveness checks remain bounded.                             | Fixed in repository |
| M-12 | Admin dashboard counts and error handling could silently show misleading zero/empty states.                | Operators make moderation or revenue decisions from incorrect data.                   | Exact server aggregates, explicit API errors, loading/empty/error states, and token-scoped query keys replaced silent fallbacks.                         | Fixed in repository |

## Deployment and residual operational work

No known source vulnerability is intentionally left open, but these tasks require the deployment owner or a connected staging environment:

1. Apply all forward Supabase migrations through `20260710300000_final_access_boundary.sql` in order to an environment that already has the recorded May migration history. The local review environment did not have a running PostgreSQL/Supabase container, so SQL was statically cross-checked but not executed against a live clone.
2. Do not use the historical May chain to bootstrap a fresh branch database: the committed baseline has pre-existing ordering/schema assumptions that prevent a clean replay. Create and review a separate squashed bootstrap before provisioning a new database from this branch.
3. Query `supabase_migrations.schema_migrations` for version `20260519120000` before deployment. Two historical source files used that version; the unsafe opt-in variant remains excluded, while the active `email_automations` migration must match the remote record.
4. Back up production, check for duplicate non-null Razorpay order/payment IDs, and test anonymous/owner/admin/service-role access in staging before applying the July chain.
5. Configure strong server secrets: service role, Razorpay secret/webhook secret, Resend API/webhook secret, and `CRON_SECRET`.
6. Configure Razorpay events for capture/order payment plus the supported refund/dispute/failure lifecycle, and Resend delivery/bounce/complaint events.
7. Reconcile legacy payment rows, especially captured payments lacking version-2 snapshots, and resolve `manual_review_reason` cases.
8. Review any pre-existing publicly accessible certificate/resume objects and migrate or delete them; policy changes do not retract URLs already copied elsewhere.
9. Run staging smoke tests for real provider signatures, email deliverability, cron invocation, Storage signed URLs, and admin workflows.
10. Monitor payment manual-review queues, suppressed recipients, cron failures, and `admin_audit_log` after release.

## Review limitations

- No production or staging credentials were used.
- A fresh Supabase database was not provisioned because the legacy May migration history requires a separately reviewed squashed bootstrap; the July hardening chain targets existing environments with matching migration history.
- No remote database migration, external email, payment, refund, dispute, or webhook event was executed.
- Provider correctness was tested through signed fixtures/mocks and source review; a staging integration test remains required.
- Dependency audit results are time-sensitive and must continue to run in CI.
